Below is an implementation-ready PROGRAM_REQUIREMENTS.md specification.

Academic Idea to CFG Generator

GitHub Copilot Prolog Agent Program Requirements

1. Project name

Working name:

IdeaCFG

Alternative command name:

ideacfg

IdeaCFG is a SWI-Prolog system that converts descriptions of human arts, sciences, humanities, professional disciplines, algorithms and other academic ideas into executable context-free grammars.

Before or during grammar generation, the system must identify mathematical, logical and directly computable operations. These operations must be removed from the ordinary CFG structure and compiled into deterministic Prolog predicates wherever direct computation is clearer, more accurate or more efficient than grammar enumeration.

The resulting system combines:

natural-language or structured idea
        ↓
concept and operation extraction
        ↓
direct Prolog computation layer
        +
CFG or DCG symbolic structure layer
        ↓
executable Prolog program
        ↓
generation, parsing, explanation and testing

The first release must target SWI-Prolog.

⸻

2. Mission

The program must convert an academic idea into two coordinated components:

1. A CFG or Prolog DCG representing symbolic, categorical, compositional, linguistic, artistic or conceptual possibilities.
2. A deterministic Prolog computation layer representing mathematical operations, comparisons, measurements, transformations, constraints and calculations.

The system must support ideas from fields including, but not limited to:

* mathematics;
* computing;
* physics;
* chemistry;
* biology;
* medicine as an academic domain;
* economics;
* business;
* law;
* philosophy;
* linguistics;
* literature;
* music;
* visual art;
* architecture;
* history;
* geography;
* education;
* psychology;
* sociology;
* engineering;
* design;
* film;
* theatre;
* logic;
* statistics;
* data science;
* interdisciplinary research.

The system must not claim that every human idea is inherently context-free. Instead, it must approximate complex ideas using explicit, inspectable grammar tricks and move non-context-free or computational behaviour into Prolog predicates, bounded structures, feature arguments, constraints or post-processing stages.

⸻

3. Core design principle

The system must apply the following rule:

Represent choices and composition with grammar.
Represent calculation and verification with Prolog.

Examples:

Musical phrase structure        → CFG/DCG
Transposition by seven semitones → Prolog arithmetic
Chemical reaction pattern       → CFG/DCG
Molar-mass calculation          → Prolog arithmetic
Essay structure                 → CFG/DCG
Word-count calculation          → Prolog arithmetic
Economic scenario structure     → CFG/DCG
Compound-interest calculation   → Prolog arithmetic
Geometric construction steps    → CFG/DCG
Distance and area calculations  → Prolog arithmetic
Narrative possibilities         → CFG/DCG
Timeline consistency checks     → Prolog constraints

The program must preserve a visible boundary between generated grammar rules and directly executed operations.

4. Primary use cases

The program must support at least the following use cases.

4.1 Generate a CFG from a plain-language idea

Example input:

A sonata contains an exposition, development and recapitulation.
The exposition introduces a first theme and a contrasting second theme.
Themes may be varied by inversion, augmentation or transposition.
Transposition changes every pitch by an integer number of semitones.

Expected output:

* grammar rules for sonata structure;
* grammar rules for theme selection and variation;
* a direct Prolog predicate for transposition;
* documentation explaining which parts became grammar and which became computation.

4.2 Generate a CFG from structured facts

Example input:

concept(photosynthesis).
stage(light_dependent_reactions).
stage(calvin_cycle).
precedes(light_dependent_reactions, calvin_cycle).
requires(calvin_cycle, carbon_dioxide).
operation(glucose_energy, multiplication).

The system must generate an executable DCG and direct predicates where applicable.

4.3 Parse an example using a generated grammar

Example:

?- idea_parse(photosynthesis, Tokens, Tree).

4.4 Generate valid examples

Example:

?- idea_generate(sonata, Output).

4.5 Compute extracted operations

Example:

?- idea_compute(compound_interest,
                [principal-1000, rate-0.05, periods-10],
                Result).

4.6 Explain the conversion

Example:

?- idea_explain(sonata, Explanation).

The explanation must identify:

* source statements;
* concepts;
* relationships;
* extracted operations;
* grammar productions;
* bounded approximations;
* assumptions;
* unresolved ambiguities.

4.7 Export generated Prolog

Example:

?- idea_export(sonata, 'generated/sonata_cfg.pl').

4.8 Generate from input/output examples

The system should optionally infer a grammar skeleton from examples:

example_input_output(
    harmonic_progression,
    [tonic, predominant, dominant],
    valid_progression
).

This functionality may use Spec-to-Algorithm-style synthesis where useful.

5.5 Existing Prolog knowledge bases

The system should accept selected facts and rules from an existing module and construct a grammar-oriented representation from them.

It must not silently alter the original module.

6. Output forms

The system must produce one or more of the following.

6.1 Prolog DCG

Preferred executable representation:

sonata(Tree) -->
    exposition(Exposition),
    development(Development),
    recapitulation(Recapitulation),
    {
        Tree = sonata(
            Exposition,
            Development,
            Recapitulation

6.2 Plain CFG notation

Example:

SONATA → EXPOSITION DEVELOPMENT RECAPITULATION
EXPOSITION → FIRST_THEME SECOND_THEME
VARIATION → INVERSION | AUGMENTATION | TRANSPOSITION

6.3 Direct Prolog predicates

Example:

transpose_pitch(Pitch, Semitones, Result) :-
    must_be(integer, Pitch),
    must_be(integer, Semitones),
    Result is Pitch + Semitones.

The system must maintain an internal representation that separates:

* recursion;
* features;
* dependencies;
* operations;

6.5 Conversion report

The conversion report must be available as:

7. Processing pipeline

The required pipeline is:

1. Read input
2. Segment source statements
3. Detect domain and terminology
4. Extract concepts and relations
5. Identify mathematical and directly computable operations
6. Remove or isolate direct operations from grammar candidates
7. Construct a typed intermediate idea model
8. Select CFG conversion tricks
9. Generate grammar rules
10. Generate direct Prolog predicates
11. Insert interfaces between grammar and computation
12. Detect left recursion, cycles and uncontrolled expansion
13. Simplify and factor grammar
14. Validate generated code
15. Run generated tests
16. Emit Prolog, CFG notation and explanation

Stages 5 and 6 may run before conceptual grammar construction or as a secondary analysis pass.

The user must be able to select:

operation_extraction(prior).
operation_extraction(secondary).
operation_extraction(iterative).

Default:

operation_extraction(iterative).

In iterative mode, operations are first extracted before grammar construction and then checked again after the initial grammar has been generated.

8. Mathematical-operation extraction

8.1 Purpose

Mathematical and directly computable operations must not be inefficiently represented as large lists of grammar alternatives when Prolog can compute them directly.

For example, the system must prefer:

Area is Width * Height

over a grammar enumerating possible widths, heights and areas.

8.5 Operation classification

Each extracted operation must be classified as one of:

operation_class(arithmetic).
operation_class(comparison).
operation_class(aggregation).
operation_class(transformation).
operation_class(constraint).
operation_class(lookup).
operation_class(logical).
operation_class(probabilistic).
operation_class(symbolic).
operation_class(external).
operation_class(unknown).

8.6 Directness decision

The system must determine whether an operation should be:

execution_mode(direct_prolog).
execution_mode(cfg_enumeration).
execution_mode(hybrid).
execution_mode(deferred).
execution_mode(unsupported).

Default rule:

Use direct Prolog when a deterministic operation can compute the result.
Use CFG alternatives when the operation represents qualitative choices.
Use hybrid mode when grammar selects an operation and Prolog performs it.

8.7 Hybrid operation example

Grammar:

transformation(transpose(Semitones)) -->
    [transpose, by, Semitones],
    { integer(Semitones) }.

Computation:

apply_transformation(
    transpose(Semitones),
    InputPitches,
    OutputPitches
) :-
    maplist(add_semitones(Semitones), InputPitches, OutputPitches).

8.8 Operation dependencies

The system must build a dependency graph:

operation_dependency(Output, Input).

It must topologically order deterministic calculations when possible.

Example:

radius → area
radius → circumference
area + height → volume

8.9 Avoid unsafe evaluation

The generator must not construct arbitrary source strings and execute them using unrestricted call/1, consult/1 or term_string/2.

Generated operations must be assembled from an allowlisted internal operation model.

Unsafe or unknown formulas must be emitted as unresolved obligations rather than executed.

10. General CFG conversion tricks

The system must implement a library of explicit CFG conversion tricks.

Each trick must:

* have a unique name;
* specify when it applies;
* specify its transformation;
* report its assumptions;
* generate tests;
* be independently enabled or disabled.

10.1 Category abstraction

Convert related items into a category.

Input:

A painting can use oil, acrylic or watercolour.

Output:

MEDIUM → OIL | ACRYLIC | WATERCOLOUR

10.2 Sequence extraction

Input:

An experiment contains a hypothesis, method, results and conclusion.

Output:

EXPERIMENT → HYPOTHESIS METHOD RESULTS CONCLUSION

10.3 Alternative extraction

Input:

A proof may use induction, contradiction or construction.

Output:

PROOF_METHOD → INDUCTION | CONTRADICTION | CONSTRUCTION

10.4 Optionality

Input:

A report may include an appendix.

Output:

REPORT → BODY OPTIONAL_APPENDIX
OPTIONAL_APPENDIX → APPENDIX | ε

10.5 Bounded repetition

Input:

A paragraph contains one or more sentences.

Output:

PARAGRAPH → SENTENCE MORE_SENTENCES
MORE_SENTENCES → SENTENCE MORE_SENTENCES | ε

The generator must support explicit maximum bounds where uncontrolled generation would be unsafe.

10.6 Recursive hierarchy

Input:

A section may contain subsections.

Output:

SECTION → CONTENT SUBSECTIONS
SUBSECTIONS → SECTION SUBSECTIONS | ε

Recursive rules must receive termination and depth analysis.

10.7 Feature splitting

Finite dependencies must be compiled into specialised nonterminals or DCG arguments.

Example:

statement(Domain, Level) -->
    subject(Domain, Level),
    predicate(Domain, Level).

This trick handles finite agreement, domain, tense, role, stage, genre, scale or other categorical information.

10.8 State threading

Processes with changing state must use DCG arguments or explicit state predicates.

process(State0, State) -->
    step(State0, State1),
    process(State1, State).

State must not be hidden inside unsafe global predicates.

10.9 Construction-specific grammar

Domain-specific structures may receive dedicated rules.

Examples:

SONNET
LAB_REPORT
LEGAL_ARGUMENT
CHEMICAL_REACTION
BUSINESS_CASE
HISTORICAL_TIMELINE
ALGORITHMIC_PROOF
MUSICAL_CADENCE

10.10 Lexical equivalence classes

Variant terms must be mapped to one concept.

lexical_form(Concept, Domain, Surface).

Examples:

plus
added to
increased by
the sum of

may map to the shared operation addition.

10.11 Synonym normalisation

Synonyms should be normalised before grammar generation but preserved as optional surface forms where requested.

10.12 Template expansion

Repeated patterns may be generated from templates.

template(
    causal_statement,
    [cause, connector, effect]
).

10.13 Common-prefix factoring

Input:

ARGUMENT → CLAIM EVIDENCE
ARGUMENT → CLAIM EXAMPLE
ARGUMENT → CLAIM COUNTERARGUMENT

Output:

ARGUMENT → CLAIM SUPPORT
SUPPORT → EVIDENCE | EXAMPLE | COUNTERARGUMENT

10.14 Common-suffix factoring

Shared endings must be factored where this improves readability or parsing.

10.15 Left-recursion elimination

Input:

EXPR → EXPR "+" TERM | TERM

Output:

EXPR → TERM EXPR_TAIL
EXPR_TAIL → "+" TERM EXPR_TAIL | ε

Arithmetic itself should then be computed by direct Prolog evaluation rather than merely recognised.

10.16 Precedence-layer construction

Expressions must be transformed into levels:

EXPRESSION
TERM
FACTOR
PRIMARY

The grammar parses structure; Prolog computes the result.

10.17 Bounded cross-dependency approximation

Dependencies that are not naturally context-free must be represented through one of:

* finite feature arguments;
* bounded grammar expansion;
* indexed categories;
* state threading;
* post-parse validation;
* direct Prolog constraints;
* explicit declaration that the structure is an approximation.

The system must not silently describe a non-context-free dependency as exactly context-free.

10.18 Semantic filtering

A broad CFG may generate candidates that are filtered by deterministic Prolog checks.

valid_candidate(Tree) :-
    domain_constraints(Tree).

The report must distinguish grammar acceptance from semantic validation.

10.19 Generate broadly, validate narrowly

For difficult domains, the system may:

1. use a CFG to generate structural candidates;
2. apply Prolog predicates to eliminate invalid candidates.

This trick must be configurable because it may generate large search spaces.

10.20 Parse narrowly, interpret broadly

The system may use a small normalised grammar and map varied surface inputs into canonical concepts during preprocessing.

10.21 Milestoning

Large academic processes should be broken into milestone nonterminals.

Example:

RESEARCH_PROJECT
  → QUESTION_STAGE
    LITERATURE_STAGE
    METHOD_STAGE
    ANALYSIS_STAGE
    REPORTING_STAGE

Milestoning should reduce grammar complexity and improve explanation.

10.22 Domain partitioning

Large ideas must be divided into domains or subdomains before grammar synthesis.

domain(physics, mechanics).
domain(physics, thermodynamics).
domain(music, harmony).
domain(music, form).

Only relevant domain grammar modules should be loaded for a query.

10.23 Hotlist rules

The system may construct a small set of highly relevant productions for a requested task instead of executing the entire domain grammar.

10.24 Decision-tree grammar selection

Where context determines a small set of valid productions, the system may compile conditions into deterministic decision predicates.

select_rule(Context, RuleId).

The selected rule may then invoke the corresponding DCG.

10.25 Table-driven grammar

Repeated factual relationships may be stored as tables rather than separate handwritten rules.

production(Category, Expansion).

An interpreter or compiler may convert the table into executable DCG clauses.

10.26 Meta-rule instantiation

Reusable academic patterns should be represented as meta-rules.

Examples:

classification
comparison
cause and effect
problem and solution
hypothesis and test
claim and evidence
part and whole
process and stage
input and transformation and output

10.27 Example-guided restriction

Examples supplied by the user may restrict generated rules and remove unsupported alternatives.

10.28 Negative constraints

Statements such as:

A conclusion must not introduce new evidence.

must become Prolog constraints rather than awkward grammar enumeration where appropriate.

10.29 Unit-aware calculation

Values with units must be represented explicitly.

quantity(Value, Unit).

Unit conversion must occur in direct Prolog predicates.

The program must reject incompatible operations such as adding metres to seconds unless an explicit domain rule defines the operation.

10.30 Probabilistic concepts

A probability distribution may be described by grammar, but probability calculations must be executed directly.

The initial system must not pretend that weighted CFG generation is an ordinary CFG unless weighted mode is explicitly selected.

17. Ambiguity handling

The system must preserve ambiguity rather than silently selecting an interpretation.

Example:

A researcher observes a student with a telescope.

Possible structures must be reported explicitly.

Representation:

ambiguity(
    telescope_attachment,
    [
        observes_with_telescope,
        student_has_telescope
    ],
    Source
).

Modes:

ambiguity_mode(report).
ambiguity_mode(generate_all).
ambiguity_mode(prefer_simple).
ambiguity_mode(require_resolution).

Default:

ambiguity_mode(report).

When generating code automatically, unresolved interpretations may be represented as grammar alternatives if safe.

18. Validation requirements

The generated system must perform the following checks.

18.1 Grammar validation

* undefined nonterminals;
* unreachable nonterminals;
* unproductive nonterminals;
* direct left recursion;
* indirect left recursion;
* epsilon cycles;
* duplicate productions;
* uncontrolled recursion;
* excessive branching;
* grammar-symbol name collisions;
* terminals accidentally treated as variables;
* nonterminating generation risk.

18.2 Operation validation

* undefined inputs;
* undefined output;
* cyclic dependencies;
* division by zero risk;
* incompatible units;
* unsafe arithmetic;
* unsupported symbolic expression;
* nondeterministic direct predicate;
* missing type checks;
* invalid date or time calculations;
* overflow or resource warnings where relevant.

18.3 Interface validation

The system must ensure that values passed between grammar and computation layers have compatible representations.

18.4 Generated Prolog validation

Generated code must:

* load without syntax errors;
* avoid singleton-variable warnings where possible;
* avoid accidental choicepoints in declared deterministic predicates;
* avoid unrestricted meta-calls;
* avoid dynamic code execution;
* use qualified module calls;
* expose only documented public predicates.

⸻

19. Determinism

Direct mathematical and operational predicates should be deterministic or semideterministic.

Declarations should be represented internally:

determinism(Operation, det).
determinism(Validator, semidet).
determinism(Parser, nondet).
determinism(Generator, nondet).

The generated test suite must check deterministic predicates for unintended residual choicepoints.

Grammar generation and parsing may be nondeterministic because alternatives are a core feature of CFGs.

The report must distinguish useful grammar nondeterminism from accidental computational nondeterminism.

⸻

20. Resource control

The system must protect against grammar explosion.

Required limits:

maximum_rules(5000).
maximum_alternatives_per_rule(100).
maximum_generation_depth(20).
maximum_generated_tokens(500).
maximum_operation_dependencies(1000).
maximum_examples(10000).

These values must be configurable.

Before expanding a grammar, estimate:

* number of rules;
* branching factor;
* likely generation depth;
* possible number of generated structures;
* recursion risk;
* memory requirements.

When limits are exceeded, the system should:

1. partition the domain;
2. create milestones;
3. factor common productions;
4. replace enumeration with direct computation;
5. add bounded recursion;
6. ask for or record assumptions;
7. emit a warning or controlled error.

⸻

21. Optimisation requirements

The optimiser must support:

* duplicate rule removal;
* unreachable rule removal;
* unproductive rule removal;
* common-prefix factoring;
* common-suffix factoring;
* lexical-table extraction;
* category merging when semantically safe;
* left-recursion elimination;
* bounded-recursion insertion;
* deterministic operation extraction;
* repeated-condition memoisation;
* indexing operation predicates;
* domain partitioning;
* hotlist grammar extraction;
* rule ordering for common cases;
* optional tabled parsing for recursive grammars;
* simplification of single-production categories.

22. Mathematical expression grammar

The project must include a reusable expression grammar.

Example structure:

expression(AST) -->
    term(Term),
    expression_tail(Term, AST).
term(AST) -->
    factor(Factor),
    term_tail(Factor, AST).
factor(number(Number)) -->
    number_token(Number).
factor(variable(Name)) -->
    variable_token(Name).
factor(AST) -->
    ['('],
    expression(AST),
    [')'].

The grammar must produce an AST.

A separate evaluator must compute it:

evaluate(number(Number), _, Number).
evaluate(variable(Name), Environment, Value) :-
    memberchk(Name-Value, Environment).
evaluate(add(A, B), Environment, Result) :-
    evaluate(A, Environment, AValue),
    evaluate(B, Environment, BValue),
    Result is AValue + BValue.

Do not mix parsing and unrestricted evaluation.

The evaluator must use an allowlist of supported operators.

The system must:

* avoid unrestricted call/1 on generated user terms;
* avoid shell/1;
* avoid arbitrary file loading from generated content;

36. Final guiding rule

The implementation must repeatedly apply this decision:

representation_for(Element, direct_prolog) :-
    directly_computable(Element),
    deterministic_or_semidet(Element),
    safe_to_execute(Element),
    !.
representation_for(Element, cfg) :-
    compositional_choice(Element),
    !.
representation_for(Element, hybrid) :-
    grammar_selects_operation(Element),
    !.
representation_for(Element, constrained_cfg) :-
    structurally_context_free_approximation(Element),
    requires_semantic_validation(Element),
    !.
representation_for(Element, unresolved) :-
    report_limitation(Element).

The cut shown above is illustrative pseudocode only. The implementation may replace it with explicit deterministic branching.

The conceptual principle is:

Do not force calculations into a grammar.
Do not force creative or conceptual alternatives into arithmetic.
Use CFGs to express possible structures.
Use Prolog to calculate, constrain, validate and explain them.

The requirements can be adapted to integrate directly with S2A, Starlog, Loop2, PLOP, Detlog or Piglog-style optimisation stages.
